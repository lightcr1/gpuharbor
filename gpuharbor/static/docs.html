Überblick

GPUHarbor ist eine selbst gehostete Steuerzentrale für KI-Modelle, die auf RunPod-GPUs laufen. Es verwaltet einen Pod, lädt ein Modell und stellt es über eine OpenAI-kompatible API bereit.

Browser → GPUHarbor-Controller → RunPod-Pod → Runtime-Image → Modell

Der Controller selbst braucht keine GPU. Er läuft auf einem kleinen Server oder im Heimnetz; nur der Pod kostet Geld.

Erste Schritte

./scripts/install                          # lokal, nur HTTP
./scripts/install --bind-ip 10.10.40.100   # im LAN/VPN erreichbar
./scripts/install --bind-ip 0.0.0.0 --https 10.10.40.100 --tls-port 9443

Danach http://<ip>:8080 öffnen. Benutzer admin, Passwort aus GPUHARBOR_ADMIN_PASSWORD in .env.

Standardmäßig sind kostenpflichtige Aktionen gesperrt. Erst mit RUNPOD_ALLOW_BILLABLE_ACTIONS=true kann ein Pod gestartet werden.

Modelle

Ein „Modell" ist ein Profil: es beschreibt, welches Modell von Hugging Face geladen wird, mit welcher Runtime, welchen Standardwerten und auf welchen GPUs. Die Gewichte werden nicht mit GPUHarbor verteilt, sondern beim ersten Start vom Pod heruntergeladen und im Pod-Volume zwischengespeichert.

GPUs

Das Dashboard lädt den echten RunPod-Katalog mit Verfügbarkeit und Preis. Ist die API nicht erreichbar, wird eine feste Liste als Fallback angezeigt.

WertBedeutung
NONEDiese GPU ist aktuell nirgends verfügbar — ein Start scheitert.
LOWWenig Kapazität; kann sich jederzeit ändern.
MEDIUM/HIGHGute Chancen auf einen Start.

Faustregel VRAM: FP8/BF16 brauchen etwa 1,3× der Modellgröße. Ein 27B-FP8-Modell (~31 GB) passt auf 48 GB. GGUF ist kleiner, aber Kontext kostet zusätzlich.

CUDA-Hinweis: Ältere Runtime-Images (CUDA 12.x) laufen nicht zuverlässig auf brandneuen GPUs (z. B. Blackwell), die CUDA 13 erwarten.

Regionen & Rechenzentren

Statt jeden Standort einzeln zu wählen, kannst du eine Region auswählen (z. B. Europa oder Nordamerika). GPUHarbor fragt dann die Rechenzentren dieser Region ab und weist automatisch einen freien zu. Für Spezialfälle lässt sich weiterhin ein konkretes Rechenzentrum wählen.

Feste Vorgabe in .env: RUNPOD_DATACENTER_IDS=EU-SE-1,CA-MTL-1.

Das Volume hängt am Rechenzentrum. Bei einem Standortwechsel wird ein neuer Pod mit neuem Volume erstellt — der Modell-Cache geht dabei verloren.

Startparameter

Diese Werte kannst du beim Start überschreiben, ohne das Profil zu ändern: Kontext, Sequenzen, GPU-Nutzung, GPU, Region/Rechenzentrum und Volume.

Bei einem bestehenden Pod lassen sich nur Kontext, Sequenzen und GPU-Nutzung gefahrlos ändern. GPU, Rechenzentrum und Volume sind fest — dafür muss der Pod gelöscht und neu erstellt werden. GPUHarbor verhindert stille Änderungen über einen Profil-Fingerprint.

Löschen ist endgültig. Das Löschen ist die einzige Aktion, die alle laufenden Kosten beendet.

Kosten

  • GPU: pro Stunde, abhängig von der GPU (z. B. A40 ca. 0,49 USD/h).
  • Volume: laufend, auch wenn der Pod gestoppt ist. Das ist der häufig übersehene Teil.
  • Download: das erste Laden eines Modells dauert je nach Größe mehrere Minuten GPU-Zeit.

Der Idle-Stop beendet die GPU nach RUNPOD_IDLE_STOP_MINUTES ohne Modellverkehr. Er beendet nicht die Volume-Kosten.

Modellkatalog & Updates

  • Mitgelieferte Profile sind schreibgeschützt; eine Änderung erzeugt ein Override.
  • Neue Built-ins erscheinen nach einem Update automatisch.
  • Eigene Profile bleiben unberührt. Export/Import als JSON ist im Dashboard möglich.
  • Änderungen werden atomar geschrieben; die vorherige Fassung bleibt als .bak.

Runtimes erweitern

Eine Runtime besteht aus drei Teilen:

  1. Eintrag in registry/runtimes.json (ID, Label, Backend, GGUF-Fähigkeit).
  2. Ein Dockerfile unter runtime/, das das Gateway auf Port 8000 bereitstellt.
  3. Ein unveränderlicher Image-Digest in .env (RUNTIME_IMAGE_*).

Ein neues Backend (also nicht vLLM/llama.cpp/Bonsai) braucht zusätzlich Code in runtime/gateway.py. Normale neue Modelle brauchen das nicht — dafür reicht ein neues Profil im Dashboard.

Runtime-Images sind bewusst nicht im Browser änderbar: ein frei wählbares Image wäre beliebige Codeausführung.

Integrationen

Open WebUI und OpenHands sind optional und nutzen dieselbe OpenAI-kompatible API. Sie erhalten nur das MODEL_ACCESS_TOKEN, niemals den RunPod-Key.

docker compose -f compose.yml -f compose.openwebui.yml up -d --build
docker compose -f compose.yml -f compose.openhands.yml up -d --build

OpenHands kann Code ausführen und Dateien ändern — nur mit einem eigenen, leeren Arbeitsverzeichnis verwenden.

HTTPS

./scripts/install --bind-ip 0.0.0.0 --https 10.10.40.100 --tls-port 9443

Erzeugt eine lokale Zertifizierungsstelle in tls/ und einen TLS-Proxy. tls/local-ca.crt auf den Geräten importieren, dann https://10.10.40.100:9443/ öffnen. Setzt automatisch GPUHARBOR_COOKIE_SECURE=true.

Nicht ins Internet weiterleiten. Nur LAN oder VPN (Tailscale/WireGuard).

Sicherheit

  • Kostenpflichtige Aktionen standardmäßig gesperrt.
  • Getrennte Geheimnisse für Steuerung, Inferenz und Runtime-Gateway.
  • Session-Änderungen brauchen ein CSRF-Token; die Login-Versuche sind begrenzt.
  • RunPod-Antworten werden rekursiv um Token-/Key-Felder bereinigt.
  • Runtime-Images müssen unveränderliche Digests sein.
