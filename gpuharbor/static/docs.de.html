Überblick

GPUHarbor ist eine selbst gehostete Steuerzentrale für KI-Modelle auf RunPod. Es verwaltet einen Pod, lädt ein Modell und stellt es über eine OpenAI-kompatible API bereit.

Browser → GPUHarbor → RunPod-Pod → Runtime-Image → Modell

Der Controller braucht keine GPU. Er läuft auf einem kleinen Server; nur der Pod kostet Geld.

Erste Schritte

Installieren, starten und anmelden — in fünf Schritten:

  1. Installieren. Im Terminal im GPUHarbor-Ordner: 
    ./scripts/install
    Das schreibt die Datei .env mit zufälligen Passwörtern, startet GPUHarbor und zeigt die Adresse an. Für andere Geräte ./scripts/install --bind-ip <deine-ip>, oder ./scripts/setup für Rückfragen nutzen.
  2. Dashboard öffnen. Auf demselben Rechner http://localhost:8080, von einem anderen Gerät http://<deine-ip>:8080. Für eine sichere Verbindung siehe HTTPS.
  3. Anmelden. Benutzer admin. Das Passwort wurde für dich erzeugt. Anzeigen mit ./scripts/init-env --show-login, ein neues setzt du mit --reset-password.
  4. Optional: RunPod-Key hinterlegen. Kostenlose Prüfungen funktionieren sofort: 
    ./scripts/set-runpod-key
  5. Nur wenn du Geld ausgeben willst. RUNPOD_ALLOW_BILLABLE_ACTIONS=true in .env setzen und den Controller neu starten.

Was ist .env, und wie öffne ich sie?

.env ist eine einfache Textdatei im GPUHarbor-Ordner. Sie enthält deine Passwörter und Einstellungen. Der Name beginnt mit einem Punkt, sie ist deshalb standardmäßig versteckt.

  • Terminal (Linux, macOS, WSL): 
    nano .env     # bearbeiten (speichern: Ctrl+O, Enter; verlassen: Ctrl+X)
cat .env      # nur lesen
  • Dateimanager: „Versteckte Dateien anzeigen“ einschalten (meist Ctrl+H), dann .env öffnen.
  • Windows-Editor: Datei → Öffnen, den vollen Pfad einfügen (z. B. C:\gpuharbor\.env), Öffnen.

Suche die Zeile GPUHARBOR_ADMIN_PASSWORD=.... Alles nach dem = ist dein Login-Passwort. Diese Datei nicht weitergeben.

Von weiteren Geräten erreichbar

Zuerst darf nur der lokale Rechner verbinden. Adresse eines Laptops oder Handys genau so eintragen, wie im Browser eingegeben, dann neu starten:

./scripts/add-host 192.0.2.10 --bind-ip 0.0.0.0
docker compose up -d

192.0.2.10 ist die RFC-5737-Dokumentationsadresse — durch die eigene ersetzen. Erlaubte Adressen anzeigen: grep GPUHARBOR_TRUSTED_HOSTS .env.

Modelle

Ein „Modell" ist hier ein Profil: es beschreibt, welches Hugging-Face-Repository geladen wird, mit welcher Runtime, welchen Standardwerten und auf welchen GPUs. Die Gewichte sind nicht Teil von GPUHarbor; der Pod lädt sie beim ersten Start und legt sie auf seinem Volume ab.

GPUs

Das Dashboard lädt den echten RunPod-Katalog mit Verfügbarkeit und Preis. Ist die API nicht erreichbar, erscheint eine feste Liste.

WertBedeutung
NONEAktuell nirgends verfügbar; ein Start scheitert.
LOWWenig Kapazität, kann sich ständig ändern.
MEDIUM / HIGHGute Chancen.

Faustregel: FP8 oder BF16 brauchen etwa 1,3× der Modellgröße. Ein 27B-FP8-Modell ist rund 31 GB und passt auf 48 GB.

CUDA beachten: Images auf CUDA 12.x laufen nicht zuverlässig auf Karten, die CUDA 13 erwarten (z. B. Blackwell).

Regionen und Rechenzentren

Statt einen Standort zu wählen, wähle eine Region wie Europa oder Nordamerika. GPUHarbor fragt RunPod, welche Rechenzentren dazugehören, und weist automatisch eines zu. Ein konkretes Rechenzentrum bleibt im erweiterten Feld möglich.

Feste Liste in .env: RUNPOD_DATACENTER_IDS=EU-SE-1,CA-MTL-1.

Stehen dort nur Automatisch und Konfiguriert, konnte der Live-Katalog von RunPod nicht gelesen werden — meist weil noch kein RunPod-Key hinterlegt ist. GPUHarbor nutzt dann die feste Liste aus RUNPOD_DATACENTER_IDS. Mit hinterlegtem RunPod-Key erscheinen wieder alle echten Regionen.

Das Volume hängt am Rechenzentrum. Ein Standortwechsel bedeutet neuen Pod und neues Volume, der Modell-Cache wird also neu geladen.

Startoptionen

Beim Start überschreibbar, ohne das Profil zu ändern: Kontext, Sequenzen, GPU-Nutzung, GPU, Region bzw. Rechenzentrum und Volume.

Bei einem bestehenden Pod lassen sich nur Kontext, Sequenzen und GPU-Nutzung gefahrlos ändern. GPU, Rechenzentrum und Volume sind fest; dafür Pod löschen und neu erstellen. GPUHarbor merkt sich einen Profil-Fingerprint und verhindert stille Änderungen.

Löschen ist endgültig. Es ist die einzige Aktion, die alle laufenden Kosten beendet.

Kosten

  • GPU pro Stunde, je nach Karte (A40 ca. 0,49 USD/h).
  • Volume kostet weiter, auch wenn der Pod gestoppt ist. Das wird oft vergessen.
  • Download: der erste Start kostet mehrere Minuten bezahlte GPU-Zeit.

Der Idle-Stop beendet die GPU nach RUNPOD_IDLE_STOP_MINUTES ohne Verkehr. Die Volume-Kosten beendet er nicht.

Katalog & Updates

  • Mitgelieferte Profile sind schreibgeschützt; Änderungen werden Overrides.
  • Neue Built-ins erscheinen nach einem Update automatisch.
  • Eigene Profile bleiben unberührt. Export/Import als JSON im Dashboard.
  • Schreiben erfolgt atomar, die vorige Datei bleibt als .bak.

GPUHarbor aktualisieren

Deine Profile liegen im Daten-Volume und werden nie überschrieben. Zum Aktualisieren:

git pull
./scripts/install        # behält .env, baut neu und startet neu

Mit einem fertigen Image stattdessen: docker compose pull && docker compose up -d.

Der optionale Update-Hinweis ist standardmäßig aus. Unter Einstellungen im Kopf aktivieren; dann fragt der Controller einmal täglich die GitHub-Releases-API und zeigt einen „Update verfügbar“-Link.

Runtimes erweitern

Eine Runtime besteht aus drei Teilen:

  1. Eintrag in registry/runtimes.json (ID, Label, Backend, GGUF).
  2. Dockerfile unter runtime/, das das Gateway auf Port 8000 bereitstellt.
  3. Unveränderlicher Image-Digest in .env (RUNTIME_IMAGE_*).

Ein wirklich neues Backend (nicht vLLM, llama.cpp oder Bonsai) braucht zusätzlich Code in runtime/gateway.py. Neue Modelle brauchen das nicht.

Runtime-Images sind absichtlich nicht im Browser änderbar: ein frei wählbares Image wäre beliebige Codeausführung.

Integrationen

Open WebUI und OpenHands sind optional. Beide sprechen mit der OpenAI-kompatiblen API von GPUHarbor und bekommen nur MODEL_ACCESS_TOKEN, nie den RunPod-Key. Der Pod muss zuerst laufen.

Open WebUI (Chat-Oberfläche)

docker compose -f compose.yml -f compose.openwebui.yml up -d --build

http://localhost:3000 öffnen. Diese Erweiterung zeigt Open WebUI schon auf http://controller:8080/v1 und übergibt das Token automatisch. Das Modell über seinen API-Namen aus dem Profil wählen (z. B. chat).

Open WebUI selbst betrieben? Dann eine OpenAI-Verbindung mit Basis-URL http://controller:8080/v1 und dem Wert von MODEL_ACCESS_TOKEN als API-Key anlegen.

OpenHands Agent Canvas (führt Code aus)

mkdir -p workspace
docker compose -f compose.yml -f compose.openhands.yml up -d --build

http://localhost:3001/canvas öffnen. Als Anbieter openai/chat (oder openai/code), Basis-URL http://controller:8080/v1 und MODEL_ACCESS_TOKEN nutzen.

OpenHands kann Code ausführen und Dateien ändern. Nur mit einem leeren, eigenen Arbeitsverzeichnis verwenden.

HTTPS

./scripts/setup
./scripts/install --bind-ip 0.0.0.0 --https 192.0.2.10 --tls-port 9443

Erzeugt eine lokale Zertifizierungsstelle in tls/ und einen TLS-Proxy. tls/local-ca.crt auf den Geräten importieren, dann https://192.0.2.10:9443/ öffnen. Setzt zusätzlich GPUHARBOR_COOKIE_SECURE=true.

Nicht ins Internet stellen. Nur LAN oder VPN.

Sicherheit

  • Kostenpflichtige Aktionen standardmäßig gesperrt.
  • Getrennte Geheimnisse für Steuerung, Inferenz und Runtime-Gateway.
  • Session-Änderungen brauchen CSRF; fehlgeschlagene Logins werden begrenzt.
  • RunPod-Antworten werden um Token- und Key-Felder bereinigt.
  • Runtime-Images müssen unveränderliche Digests sein.
